> **本文档记录的是实测结果，不是推测。** 每条结论都附了复现方式。

## 1. 背景：为什么需要这份记录

用户要求准备「女生拍照」主题素材（自拍 / 他拍 / 生活打卡 / 旅行 /
咖啡馆 / 街拍），要求画面自然真实、构图与光线良好、风格统一、
年龄与穿搭多样。

本项目已确认 **keypool 不提供图像生成能力**（`/v1/images/generations`
在代理层与上游层双重 404，12 个图像模型全部失败）。因此素材只能
**从互联网获取**。

本文档记录"到底能从哪些源拿到什么"，以及各源的**硬限制**。

## 3. Picsum：唯一可用的通用摄影源，但**无主题能力**

### 3.1 硬限制：图库总量仅 993 张

实测 `https://picsum.photos/v2/list?page=N&limit=100`：

- 分页在第 **11 页**结束，累计 **993 张**，唯一 id 993 个（id 范围 0..1084）。
- `limit` 参数上限 100（传 300/500/1000 均只返回 100 条）。
- **结论：候选池无法扩大，993 就是天花板。**

### 3.2 硬限制：无主题标签

Picsum 的元数据只有 `id / author / width / height / url / download_url`，
**没有** `tags` / `scene` / `category` 之类的字段。

→ 因此**无法检索"咖啡馆""街拍""自拍"**。所有按主题的归类都只能是
人工作业，不能伪装成数据源标签。

### 3.3 实测产出率（993 张全量扫描）

| 阶段 | 通过 | 占比 |
| --- | --- | --- |
| 任意可检出主体（YOLO） | 186 / 993 | 18.7% |
| 其中可检出人脸（Haar） | 34 / 993 | 3.4% |
| 再过滤糊图（Laplacian var ≥150） | ~20 / 993 | 2.0% |
| 再过滤构图分 ≥40 | **19 / 993** | **1.9%** |

### 3.4 **人工复核发现的真实问题（关键）**

自动检测**会误判**。对 19 张通过自动筛选的图做人工目视复核，
发现约 **7 张完全不符合"女生拍照"用途**：

| 类型 | 实例 | 自动检测为何放行 |
| --- | --- | --- |
| 非人像（静物） | 一串葡萄、办公桌 | YOLO 把物体误判为 person；Haar 有误报 |
| 非人像（室内场景） | 黑白室内空间 | 同上 |
| 剪影不可辨 | 逆光人影 | 检出 person，但面部全黑 |
| 男性 / 背影 | 酒吧男服务员、男乐手 | 检出 person + 正脸 |
| 局部肢体 | 只拍到腿/脚 | 检出 person |
| 风景为主 | 人物极小 | 检出 person 但占比 <3% |

→ **去掉后实际可用约 8~12 张**，且风格、场景杂乱
（葡萄与雪山与酒吧混在一起），**不满足"整体风格统一"的要求**。

### 3.5 授权

Picsum 分发的图片来自 Unsplash，适用 [Unsplash License]
（免费商用、无需署名，但**禁止**将未修改的图片作为图库二次分发）。
每张图的 `author` 与 Unsplash 原始页已记录在 `_index.json` 与
`PROVENANCE.md`，可溯源。

## 4. thispersondoesnotexist：人像质量高，但**构图多样性为零**

### 4.1 可用性

- 实际图片地址：`https://thispersondoesnotexist.com/random-person.jpeg`
  （需带 `Referer: https://thispersondoesnotexist.com/`，否则可能被拒）
- 返回 **1024×1024** JPEG，质量高，人脸真实自然。

### 4.2 硬限制 A：缓存导致并发请求拿到重复图

实测（像素级哈希，排除 EXIF 干扰）：

| 请求方式 | 唯一内容数 |
| --- | --- |
| **并发 6 次**（同一时刻） | **2 / 6** ← 严重重复 |
| **串行 4 次**（间隔 3s） | **4 / 4** ← 正常 |

→ 必须**串行 + 加延迟**，不能并发。这会把采集 30 张的时间
拉长到至少 90s 以上。

### 4.3 硬限制 B：**所有输出都是正面免冠照**

人工目视 12 张样本（探针预览图，产物为临时文件，已随 `outputs/_probe/` 清理；
需要复现请重跑 `scripts/fetch_topic_photos.py` 的探针分支）：
全部是**面部居中、正对镜头的证件照式构图**，背景为模糊墙面。

→ **与本项目的核心价值直接冲突。** 本项目做的是"构图指导"，
需要的是**主体位置变化、留白比例、三分法、视线方向、全身/半身/特写
的不同景别**。而该源提供的是一个**恒定构图**，无法用于：

- 三分法 / 中心构图对比
- 头顶留白（headroom）分析
- 前景留白（lead room）/ 视线方向分析
- 景别（远景/全身/半身/特写）差异

→ 可用于"人脸检测链路验证"，但**不能作为构图演示素材**。

### 4.4 授权与伦理

生成式人脸，无真实人物肖像权问题。但需注意：
- 该源未提供明确的授权条款；
- 生成式人脸用于公开演示应注明来源与生成性质。

## 5. 结论与建议

### 5.1 事实汇总

| 需求项 | Picsum | tpdne | 能否满足 |
| --- | --- | --- | --- |
| 人物真实自然 | 部分 | 是 | ⚠️ |
| 构图与光线良好 | 参差 | 是（但构图固定） | ❌ |
| **整体风格统一** | ❌ 杂乱 | ✅ 高度统一 | ❌ |
| 年龄/穿搭多样 | 部分 | 是 | ⚠️ |
| **构图多样性**（本项目刚需） | ✅ | ❌ | ❌ |
| 无主题检索能力 | ❌ | ❌ | ❌ |
| 可批量获取 | ✅ | ⚠️ 需串行限速 | ⚠️ |

**没有单一图源能满足全部要求。**

### 5.2 三条可选路径（需用户决策）

**路径 A：双源混合，各取所长（推荐）**
- 用 Picsum 的 19 张 → 按**实测属性**分目录（景别/人脸/主体数/构图分），
  **人工剔除 7 张不合格**后保留约 12 张，用于**构图多样性**演示。
- 用 tpdne 串行采集约 20 张 → 单独放 `faces/` 目录，用于**人像检测链路**
  与"同一主体不同环境"的合成实验。
- 主题标签（自拍/咖啡馆/街拍）出 `topics.json`，**显式声明为人工判断**。

**路径 B：申请图源 API Key**
- Unsplash / Pexels 提供免费 API Key（Unsplash 50 req/h，Pexels 200 req/h）。
- **能真正按主题检索**（`query=cafe portrait`），彻底解决主题分类问题。
- 需要用户提供 Key 或授权我去申请（申请需邮箱注册）。
- **这是唯一能真正满足"咖啡馆/街拍/旅行"主题要求的路径。**

**路径 C：接受降级，诚实标注**
- 只保留 Picsum 人工复核通过的 ~12 张。
- 在文档中明确写：**受图源能力限制，素材库规模为 12 张，
  且无法按"自拍/咖啡馆/街拍"主题分类**。
- 可在简历中作为"**受限于合规图源，改用小规模高质量集 + 人工复核**
  的工程决策"来讲，而不是假装有 40 张。

### 5.3 无论走哪条路都必须做的

1. **人工复核不可省**：自动检测误判率约 37%（7/19），
   必须人眼过一遍，否则会把葡萄当作人像入库。
2. **provenance 必须记录**：作者 + 原始页 + 授权，逐图落盘。
3. **主题标签必须标注可信度**：不得把人工判断包装成数据源元数据。
